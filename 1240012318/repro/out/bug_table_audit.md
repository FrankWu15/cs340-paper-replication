# bug 表一致性审计

核对 `repro/data/bugs_master.csv` 与论文 artifact 的 blocking / non-blocking 两张原表，
确认复现状态没有搬运错误，并厘清「41 条」与「44 条」的口径差异。

## 1. 逐行对回原表

| 项目 | 值 |
|---|---|
| master 行数 | 171 |
| 原表 blocking 行数 | 85 |
| 原表 non-blocking 行数 | 86 |
| 原表 (uid, sha) 唯一键 | 171 |
| 搬运值不一致 | **0** |
| 在原表找不到 | 2 |

在原表找不到的行（artifact 未收录该 commit）：

- `boltdb#392` / boltdb / commit=`(空)`
- `boltdb#240` / boltdb / commit=`(空)`

这 2 条正是 artifact 中**没有补丁文件**的 bug（`boltdb#392`、`boltdb#240`），
原表里对应行的 `commit hash` 为空，因此无法用 (uid, sha) 匹配。

## 2. 两种计数口径：41 还是 44

论文正文 §4 写的是 **“reproduced 21 blocking bugs and 20 non-blocking bugs”**，
合计 **41**。而 artifact 的 CSV 里标 `1` 的行是 21 + 23 = **44**。

| 口径 | blocking | non-blocking | 合计 |
|---|---|---|---|
| 行级（补丁 commit 数） | 21 | 23 | **44** |
| bug 级（唯一 BugID） | 21 | 20 | **41** |
| 论文正文 | 21 | 20 | **41** |

**bug 级合计恰好等于论文的 41**，说明 artifact 与论文没有矛盾，
差异全部来自一个 bug 对应多个补丁 commit。

涉及多补丁的已复现 bug：

| BugID | 补丁 commit 数 | 说明 |
|---|---|---|
| `etcd#4876` | 4 | `91dc6b29a6`、`2c83362e63`、`e129223dbe`、`4bdfc0a46d` |

> **对 P4 的影响**：这类 bug 不能只回滚其中一个 commit。补丁被拆成多段时，
> 单独回滚任意一段往往不足以让 bug 复现，必须整组一起回滚。

## 3. 89 条空白行的含义

原表 `Reproduced?` 列的取值只有三种，master 原样搬运：

| 取值 | 行数 | bug 级 |
|---|---|---|
| `1` | 44 | 41 |
| `0` | 38 | 37 |
| 空白 | 89 | 89 |

**空白不是数据缺失**，是 artifact 原表本身未填写。因此不存在“补全”这回事——
原表没有值可抄，凭空填 `0` 会伪造出一批“尝试过但失败”的记录。

论文没有说明 `0` 与空白的区别。从数据分布看最自然的解释是：
`1` = 复现成功、`0` = 尝试过但未复现成功、空白 = 未尝试。
按此推断，作者实际尝试了 78 个 bug（41 成功 + 37 失败），
其余 89 个未纳入复现实验。
**此为推断，非论文原文表述**，报告中引用时应注明。

## 4. 同一 bug 内状态冲突

**无冲突**：同一个 bug 的所有补丁行复现状态完全一致，
说明 artifact 的状态是按 bug 判定的，不是按 commit 逐行判定。
这一点支持按 bug 级统计。

## 5. 结论

1. master 的 `reproduced` 值与原表**逐行一致**（0 处不一致），搬运无误。
2. 论文的 41 条 = bug 级计数；artifact 的 44 行 = 补丁 commit 级计数，两者不矛盾。
3. 89 条空白是原表原貌，不应填补；对外表述统一为
   “41 个已复现 bug（对应 44 个补丁 commit）”。
4. `etcd#4876` 的 4 个补丁 commit 在 P4 中必须整组回滚。
